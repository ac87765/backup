# Proposal

## Why

需要一个用户自己掌握密钥的文件备份服务：文件存放在阿里云 OSS，但云厂商和本服务的运营者都无法读取文件内容和文件名。仓库目前是空的，这个 change 建立整个系统的基础架构（账号、密钥体系、加密传输与存储、文件管理），并作为后续所有功能的起点。

## What Changes

- 建立 Cargo workspace（`crypto-core`、`crypto-wasm`、`server`）和 React + TypeScript 前端工程（`web/`），以及 CI、Docker 镜像、数据库迁移框架。
- 用户账号：邮箱注册、邮箱验证、登录/登出、会话管理、修改密码、使用恢复密钥重置密码。密码只在浏览器内参与密钥派生，服务端不接收明文密码。
- 客户端加密：主密钥（MK）在浏览器生成，由密码派生的密钥和恢复密钥分别包裹后存到服务端；每个文件/文件夹拥有独立的节点密钥；文件内容按块用 XChaCha20-Poly1305 加密，文件名与元数据同样加密。
- 文件传输：浏览器把密文块通过预签名 URL 直传 OSS；服务端用显式的上传会话状态机管理配额预留、分块确认、完成提交与过期清理，支持断点续传；下载时由浏览器拉取密文块并在本地校验、解密。
- 文件管理：加密文件夹树、移动/重命名、历史版本（保留策略 + 恢复）、回收站（定期清除）、每用户配额。
- 运维基线：健康检查、结构化日志、Prometheus 指标、限流、安全响应头/CSP、优雅停机、可靠的后台任务（OSS 对象删除 outbox、过期会话清理）。

### Non-goals（不在本次范围内）

- 文件/文件夹分享、多人协作、公开链接。
- 桌面客户端、移动端、CLI、文件夹自动同步（浏览器无法监听本地目录）。
- 跨文件去重（会泄露“文件相同”信息，与 E2EE 目标冲突）。
- 服务端搜索、缩略图、在线预览（服务端看不到明文）。
- 两步验证 (TOTP/WebAuthn)、OPAQUE 等 PAKE 协议：作为后续 change。
- 在既没有密码又没有恢复密钥的情况下恢复数据：这在设计上就不可能，只提供“清空账户重新开始”之外的任何恢复手段均不在范围内（MVP 连清空重置也暂不做）。
- 付费、订阅、管理后台（配额通过配置/数据库设定）。

## Capabilities

### New Capabilities

- `user-accounts`: 注册、邮箱验证、登录登出、会话、修改密码、恢复密钥重置密码、防账号枚举与暴力破解。
- `client-encryption`: 客户端密钥体系（MK、节点密钥、恢复密钥）、算法与密文格式、元数据加密、服务端可见信息的边界。
- `file-transfer`: 上传会话状态机、分块直传 OSS、断点续传、提交校验、下载与本地完整性校验、孤儿对象清理。
- `file-management`: 加密文件夹树、重命名/移动、同名冲突检测、历史版本、回收站、配额。
- `service-operations`: 配置、健康检查、日志与指标、限流、安全响应头、后台任务的可靠执行、优雅停机。

### Modified Capabilities

（无，项目首个 change）

## Impact

- 新代码：`crates/crypto-core`、`crates/crypto-wasm`、`crates/server`、`web/`、`migrations/`、`Dockerfile`、CI 配置。
- 外部依赖：PostgreSQL（建议阿里云 RDS）、阿里云 OSS（私有 bucket，需配置 CORS 与服务端加密）、SMTP（建议阿里云邮件推送 DirectMail）。
- 对外 API：`/api/v1/*` REST + OpenAPI 文档；浏览器需支持 WebAssembly、Web Worker、Web Crypto 随机数。
- 安全：密码与恢复密钥丢失即数据不可恢复，必须在注册流程中明确告知用户并强制确认已保存恢复密钥。
